# 项目技术说明

## 1. 项目定位

这是一个原始 GitHub 快照可追溯到 2020 年的本科阶段 Windows Forms 电影院订票系统。

目前更适合把它视为一个历史作品集项目，而非生产系统。项目覆盖了相对完整的端到端业务流程，但也保留了早期工程中常见的架构耦合、重复代码和可测试性不足等问题。

原始 SQL Server 数据库资产目前已不在手边，因此本仓库不能声称具备完整的 clone-and-run 可复现性。

## 3. 从源码恢复出的架构

当前 GitHub 中保存的核心项目是 WinForms UI 层：`hh.csproj`。

原工程曾通过 ProjectReference 引用：

- `Model`
- `PublicLib`

两个仓库之外的兄弟项目。它们的源码没有跟随 2020 年的上传进入 GitHub，但历史构建目录中保留了编译后的 DLL。

整理后，必要的历史二进制依赖集中保存在 `lib/`。

简化后的结构可以理解为：

```text
WinForms UI (hh)
   ├── 直接使用 ADO.NET / SQL Server
   ├── Model.dll
   ├── PublicLib.dll
   └── IrisSkin4 UI 皮肤
```

这不是严格意义上的分层架构：展示、业务规则与持久化职责存在较明显重叠。

## 4. 当前可复现性边界

目前仓库已经具备：

- UI 源码
- Visual Studio solution
- `.csproj`
- WinForms 资源文件
- 必要历史 DLL / skin 依赖

但缺少：

- `CinemaSystem` 数据库表结构
- 存储过程
- 初始 / 演示数据
- 原始 SQL Server 数据库备份

因此目前可以进行代码阅读和工程审阅，但不能仅靠本仓库恢复出与 2020 年一致的完整运行系统。

如果以后从旧电脑中找回数据库备份，最合适的补全方式不是直接上传原始数据库文件，而是先脱敏，然后导出：

1. `database/schema.sql`
2. `database/procedures.sql`
3. `database/seed.sql`

再配合 README 中的恢复说明，形成真正可复现的演示环境。

## 5. 主要技术债

### SQL 构造

部分查询直接通过字符串拼接生成 SQL。现代实现应统一改为参数化查询。

### 购票并发

当前逻辑先查询座位是否已售，再执行订单插入。由于检查与写入不是一个原子操作，两个客户端理论上可能同时看到同一座位“可用”。

生产级设计应至少包含：

- 数据库事务
- 对“场次 + 座位”建立唯一性约束
- 在数据库层保证最终一致性

### 重复的数据访问逻辑

多个 Form 重复负责连接创建、打开、异常捕获和关闭。更合理的做法是抽取独立数据访问层。

### UI / 业务强耦合

不少 WinForms 事件函数同时承担输入校验、SQL 查询、业务判断和界面更新。现代化重构时应优先分离这些职责，而不是先更换 UI 框架。

### 测试

当前没有自动化测试。由于业务逻辑高度依附于 Form 和数据库，要增加测试，需要先抽离核心规则和数据访问。

## 6. 安全整理

原始公开仓库的 `app.config` 曾包含 SQL Server `sa` 用户名和硬编码密码。

本次整理已经把当前分支改成 Windows Integrated Authentication 的非秘密示例配置。

需要注意：后续 commit 删除密码，并不会自动从旧 Git 历史中抹除它。如果该凭据曾被用于真实或长期存在的数据库，应当视为已经暴露并更换。

就本项目目前的历史用途而言，不应再在仓库中保存任何真实数据库密钥。

## 7. 如果未来继续修复，建议顺序

如果以后想把它从“历史作品”恢复成真正可运行的演示项目，优先级建议如下：

1. 找回或重建原始数据库 schema / stored procedures。
2. 补最小化 seed data。
3. 验证在兼容的 .NET Framework 4.0 环境中可以重新编译。
4. 将 SQL 拼接替换为参数化查询。
5. 为购票加入事务与数据库唯一约束。
6. 抽离数据访问逻辑。
7. 针对登录、排片、选座购票补少量 integration tests。
8. 最后再考虑是否迁移到现代 .NET / 新 UI 技术。

优先恢复**正确性与可复现性**，比直接进行框架重写更有价值。
